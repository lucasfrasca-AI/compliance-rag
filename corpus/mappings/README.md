# Mapping YAML

Hand-authored files in this directory are the **only** source of crosswalks and
obligation metadata (D-01). Nothing here is generated by an LLM.

The single exception is a tenant policy-to-law mapping, which an LLM may
*propose*. A proposal is written with `status: proposed` and is not traversed
until a human approves it by changing the status in a reviewed PR.

Changes reach the graph only through a pull request. Every file carries
`author`, `reviewed_by`, `date` and `source_clause_ids`.

## Required front matter

Every file in this directory starts with:

```yaml
author: jane.doe@example.com
reviewed_by: sam.smith@example.com   # a person, never a model (see Review)
date: 2026-09-20                     # ISO date the mapping was authored
source_clause_ids:                   # every clause the mapping is derived from
  - privacy-act-1988:C2026C00227:sch1/app11/1
```

A file missing any of these four fields fails the loader and the CI check.

## Review

One rule for every reviewed artefact with this front matter — mapping YAML,
selection manifests (`corpus/instruments/{instrument_id}/{version_id}/manifest.yaml`,
which carry `author`/`reviewed_by`/`date` minus `source_clause_ids`) and the
golden set (`corpus/golden/`). It is enforced by `validate_review` in
`compliance_rag.corpus.models`, which every loader calls:

- **Who reviewed is always a person, never a model.** That review is the
  human judgement D-01 requires of anything authoritative.
- **A model-drafted file needs a distinct human reviewer.** A model records
  itself in `author` with a `model:` prefix
  (`author: "model: Claude Opus 5.5 — …"`); since a model never reviews, the
  reviewer is necessarily someone else. The golden set is drafted this way:
  the model proposed, the reviewer's correction is the label.
- **A human may review their own file — single-author review.** The project
  has one builder, and a `reviewed_by` naming a second person who didn't
  review it would be a fiction, worse than an honest single name. Selection
  manifests are reviewed this way today (`author == reviewed_by`).

The rule depends on the `model:` prefix being written honestly — a model
recorded without it would pass as a human self-review. That is a review
discipline, not something a loader can detect.

**A distinct human reviewer is required before any corpus or mapping is used
for a real customer**, whoever authored it. When a second reviewer exists,
tighten `validate_review` so `reviewed_by != author` always, and update this
section — don't leave it standing beside a rule nobody follows.

## Obligations

```yaml
author: jane.doe@example.com
reviewed_by: sam.smith@example.com
date: 2026-09-20
source_clause_ids:
  - privacy-act-1988:C2026C00227:sch1/app11/1

obligations:
  - id: OB-APP11-1                       # stable, never reused
    clause_id: privacy-act-1988:C2026C00227:sch1/app11/1
    summary: >
      Take such steps as are reasonable in the circumstances to protect
      personal information from misuse, interference and loss.
    status: in_force                     # in_force | not_yet_commenced | repealed
    valid_from: 2014-03-12
    valid_to: null                       # null means still in force
    applies_to:                          # APPLIES_TO edges
      jurisdictions: [AU]
      sectors: []                        # empty means all sectors
      actor_roles: [apn_entity]
    requires:                            # REQUIRES edges
      conditions: [COND-SMALL-BUSINESS-THRESHOLD]
      controls: []
    supersedes: null                     # obligation id this one replaces
```

Not every clause is an obligation. Recitals and definitions are clauses without
an obligation node (`CONTEXT.md`).

## Conditions

A condition gates an obligation and is evaluated against the tenant profile.
Conditions never read a document directly: documents inform, humans assert
(`CONTEXT.md`).

```yaml
conditions:
  - id: COND-SMALL-BUSINESS-THRESHOLD
    kind: turnover                       # turnover | actor | jurisdiction | data_category
    description: Annual turnover exceeds AUD 3,000,000.
    profile_field: annual_turnover_aud
    operator: gt                         # eq | ne | gt | gte | lt | lte | in | not_in
    value: 3000000
    unassessable_reason: >
      Stated when the profile has no value for this field, so the obligation is
      reported as unassessable rather than assumed either way (D-06).
```

## Crosswalks

A `CROSSWALKS_TO` edge between obligations or controls across instruments.

```yaml
crosswalks:
  - from: OB-APP11-1
    to: iso-27001:2022:annexa/8/3
    kind: partial                        # equivalent | partial | related
    note: >
      ISO annexa/8/3 covers access restriction only; APP 11.1 is broader and also
      covers misuse, interference and loss.
```

`kind` is a human judgement and is displayed as such. It is never rendered as a
score (D-06).

## Tenant policy-to-law proposals

```yaml
policy_mappings:
  - id: MAP-ACME-SEC2-APP11
    policy_clause_id: acme-policy:v3:sec2/1
    obligation_id: OB-APP11-1
    kind: partial
    status: proposed                     # proposed | approved | rejected
    proposed_by: llm                     # llm | human
    approved_by: null                    # required before status may be approved
    approved_date: null
```

A mapping with `status: proposed` is stored, shown in the approval queue, and
never traversed. Only `approved` mappings reach Track A.

## Stable IDs

Obligation and condition IDs are stable forever. Correcting a mapping edits the
existing entry; replacing an obligation creates a new ID and sets `supersedes`
on the new one and `valid_to` on the old (D-05). IDs are never reused.
